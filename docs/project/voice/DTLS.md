# DTLS Transport Security

This document explains the WebRTC transport security layer used by GoChat voice.

It covers:

- what DTLS secures between the browser and the SFU
- how the SFU certificate is configured
- what the frontend must do, and what it should not do
- how DTLS relates to DAVE end-to-end encryption

## What DTLS Does In GoChat

GoChat voice uses standard WebRTC transport security:

- ICE establishes network connectivity
- DTLS authenticates the peer connection and negotiates SRTP keys
- SRTP encrypts RTP and RTCP packets on the wire between client and SFU

In practice, that means media is encrypted in transit even when DAVE is not active.

## What The SFU Presents

The SFU presents a DTLS certificate during WebRTC negotiation.

GoChat supports two server-side modes:

- explicit certificate and key via `dtls_certificate_file` and `dtls_private_key_file`
- automatic self-signed certificate generation at SFU startup when those fields are left empty

You can generate a reusable PEM pair with:

```bash
go run ./cmd/tools certificates dtls generate \
  --cert-out ./certs/sfu.crt \
  --key-out ./certs/sfu.key \
  --common-name sfu-eu-1
```

Then point the SFU config at those files:

```yaml
dtls_certificate_file: "./certs/sfu.crt"
dtls_private_key_file: "./certs/sfu.key"
```

When to use explicit files:

- production deployments where you want controlled certificate rotation
- multi-restart environments where a stable certificate fingerprint helps debugging
- environments where operators want the certificate material managed outside the running process

When generated-at-startup is fine:

- local development
- disposable review environments
- early staging setups where operational simplicity matters more than stable fingerprints

## How Browsers Use DTLS

Frontend code does not implement the DTLS handshake itself.

The browser handles that automatically inside `RTCPeerConnection` after SDP exchange:

1. The client creates an offer.
2. The SFU answers with SDP that includes DTLS fingerprint lines.
3. The browser applies that SDP with `setRemoteDescription(...)`.
4. The browser and SFU complete the DTLS handshake internally.
5. WebRTC starts sending encrypted SRTP media.

That means the frontend does not need to:

- read the SFU PEM files
- load the SFU certificate into JavaScript
- manually validate the DTLS certificate
- start a separate DTLS socket

## What The Frontend Must Do

For GoChat `v=2` clients, DTLS works as long as the frontend follows the normal WebRTC flow correctly.

Required frontend behavior:

- connect to the SFU signaling endpoint with `wss://` in production
- create `RTCPeerConnection` from the `Ready (2)` `ice_servers`
- send the SDP generated by the browser without stripping DTLS attributes
- apply the SFU answer or offer with `setRemoteDescription(...)`
- let the browser complete ICE and DTLS before expecting media

The most important rule is:

- do not remove or rewrite `a=fingerprint` and `a=setup` lines when munging SDP

Those attributes are part of DTLS negotiation.

## Recommended Frontend Shape

This is enough for DTLS to work on the browser side:

```ts
const pc = new RTCPeerConnection({
  iceServers: ready.ice_servers,
});

const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
await waitForIceGatheringComplete(pc);

gateway.send({
  op: GatewayOp.SelectProtocol,
  d: {
    protocol: "webrtc",
    type: "offer",
    sdp: pc.localDescription?.sdp,
    rtc_connection_id: rtcConnectionId,
  },
});

await pc.setRemoteDescription({
  type: payload.type,
  sdp: payload.sdp,
});
```

DTLS is negotiated by the browser as part of that `RTCPeerConnection` lifecycle.

## What The Frontend Should Not Configure

For browser clients, do not try to mirror the SFU certificate configuration in JavaScript.

Avoid these patterns:

- passing custom certificate material from the server into the web app
- trying to pin the SFU PEM output in frontend code
- replacing the browser-generated local DTLS certificate
- removing `a=fingerprint` lines during SDP rewriting
- hard-coding ICE servers instead of using `Ready.ice_servers`

If you are building a native client later, certificate pinning may be a separate design choice. That is not part of the current web frontend contract.

## Operational Requirements Around DTLS

DTLS secures the media path, but production web clients still need normal browser-safe delivery:

- serve the frontend over `https://`
- use `wss://` for SFU signaling
- avoid mixed-content setups where an HTTPS app tries to open insecure signaling
- keep microphone and camera access behind a secure origin

The browser will usually refuse or degrade media access if the page origin is not secure.

## How To Debug DTLS Problems In The Frontend

If ICE succeeds but media still fails, inspect DTLS state before assuming a codec or DAVE problem.

Useful checks:

- `pc.connectionState`
- `pc.iceConnectionState`
- `pc.iceGatheringState`
- browser WebRTC internals
- `RTCPeerConnection.getStats()`

Example helper:

```ts
export async function inspectTransport(pc: RTCPeerConnection) {
  const stats = await pc.getStats();

  for (const report of stats.values()) {
    if (report.type !== "transport") {
      continue;
    }

    console.log("transport", {
      dtlsState: report.dtlsState,
      iceRole: report.iceRole,
      selectedCandidatePairId: report.selectedCandidatePairId,
      localCertificateId: report.localCertificateId,
      remoteCertificateId: report.remoteCertificateId,
    });
  }
}
```

Healthy transport usually looks like:

- ICE reaches `connected` or `completed`
- DTLS reaches `connected`
- the peer connection reaches `connected`

If SDP munging broke DTLS negotiation, the browser may never move the transport to a healthy DTLS state.

## DTLS And DAVE Are Different Layers

DTLS and DAVE solve different problems:

- DTLS-SRTP protects media on the wire between each client and the SFU
- DAVE protects encoded media end-to-end above the transport layer

So the security model is:

- without DAVE: encrypted transport, SFU can access media
- with DAVE: encrypted transport plus end-to-end media protection

DTLS is always relevant. DAVE is an additional layer for eligible `v=2` sessions.

## Frontend Checklist

Before shipping a frontend voice client, verify:

1. The app is loaded from `https://`.
2. The SFU signaling URL is `wss://.../signal?v=2`.
3. The client uses `Ready.ice_servers`.
4. The client sends and applies SDP without stripping DTLS attributes.
5. The peer connection reaches healthy ICE and DTLS transport states.
6. Media still connects when DAVE is disabled, proving the DTLS-SRTP baseline is sound.
