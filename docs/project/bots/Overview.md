# Overview

Bots are stored as normal users in `users` with `UserFlagBot` set in `users.flags`. This keeps profile, member, role, guild, and channel permission behavior aligned with regular users while exposing bot identity through `is_bot` in user and member DTOs.

Additional bot records are stored separately:

| Table | Purpose |
|-------|---------|
| `bots` | Owner, description, public visibility, default permissions, disabled state |
| `bot_tokens` | Named hashed runtime tokens, shown only once at creation |
| `bot_install_grants` | Signed install grants with requested permissions, expiry, and use limits |
| `bot_guilds` | Installed bot per guild with granted permission cap and installer metadata |

Runtime tokens are opaque tokens generated by the service. The raw token is never stored; only its hash and prefix are persisted.

## Service Boundaries

| Service | Responsibility |
|---------|----------------|
| `cmd/api` | User-authenticated bot management and guild-admin install/remove |
| `cmd/botapi` | Bot-authenticated runtime REST API |
| `cmd/botrouter` | Partitioned bot-event fan-out and permission filtering |
| `cmd/botws` | Bot-authenticated WebSocket gateway, shard delivery, and bot presence publishing |
| `cmd/ws` | Regular client WebSocket gateway |

Bot runtime services do not reuse user endpoint handlers. They may share lower-level repositories, DTOs, permission checks, and message/event models, but HTTP handler ownership stays inside bot service packages.
