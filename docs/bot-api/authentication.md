# Authentication

Bot runtime authentication is separate from normal user authentication.

Every REST request and gateway upgrade must include:

```http
Authorization: Bot <token>
```

The token itself is generated by GoChat and starts with:

```text
gcb_
```

The Go client accepts either the raw token or the full header value:

```go
goclient.New("gcb_xxx")
goclient.New("Bot gcb_xxx")
```

Both result in the same outbound header.

## Token Validation

At request time GoChat:

1. Parses the `Authorization` header.
2. Requires the `Bot` scheme.
3. Hashes the supplied token with SHA-256.
4. Looks up a stored bot token record by hash.
5. Loads the bot record and bot user.
6. Rejects disabled bots and non-bot user records.
7. Touches the token record so operators can see recent use.

Plaintext token values are not stored. Only token hashes and prefixes are stored server-side.

## Failure Modes

All authentication failures return HTTP `401`.

| Server error | Meaning |
|--------------|---------|
| `missing authorization header` | No `Authorization` header was sent |
| `bot runtime authentication requires Authorization: Bot <token>` | Header is malformed, uses a different scheme, or has an empty token |
| `invalid bot token` | Token hash, bot record, or bot user could not be validated |
| `bot is disabled` | Bot exists but is disabled |

## Headers

Recommended REST headers:

```http
Authorization: Bot gcb_xxx
Accept: application/json
Content-Type: application/json
User-Agent: MyBot/1.0
```

`Content-Type` is needed for requests with JSON bodies.

Gateway upgrade headers:

```http
Authorization: Bot gcb_xxx
User-Agent: MyBot/1.0
```

## Security Guidance

- Treat bot tokens like passwords.
- Do not ship tokens in client-side code.
- Rotate tokens after accidental exposure.
- Use a separate token per deployment environment.
- Use least-privilege install grants for each guild.
- Keep bot gateway connections on server infrastructure you control.

## Authorization vs Permissions

Authentication proves which bot is calling. Permissions decide what that bot can do after it is authenticated.

Effective guild permissions are:

```text
normal_member_role_and_channel_permissions & bot_install_granted_permissions
```

For route-level permission requirements, see the [REST API reference](rest.md#permissions-by-operation).
